## 1. Overview
LED River Protocol (LDR) is a lightweight request-response protocol built on top of UDP.

It is designed for communication between clients and LED River servers.


## 2. Terminology
- The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are to be interpreted as described in RFC 2119.

- Throughout this specification, the **LED River Protocol** is referred to as **LDR**.


### 2.1 Keywords
- **Client** – sends requests to the server.
- **Server** – receives requests and sends responses.
- **Packet** – one UDP datagram containing exactly one LDR message.

## 3. Transport
LDR uses **UDP** as the transport protocol.

Each LDR message **MUST** be carried in exactly one UDP datagram.

A UDP datagram **MUST** contain exactly one LDR message.

## 4. Data Representation

Unless stated otherwise:

- All multi-byte integer fields **MUST** be encoded in **big-endian** byte order.
- All integer fields are unsigned.
- Field sizes are expressed in octets.

## 5. Packet Format

| ------ | ---- | ---------------------------- |
| 0      | 3 B  | Magic = `0x4C` `0x44` `0x52` |

| 8      | 1 B  | Message Control              |
| 9      | 1 B  | Command                      |
| 10     | N B  | Payload                      |


### 5.1 Magic
The magic field **MUST** contain the ASCII string `LDR`
(`0x4C4452`).

Packets with an invalid magic value **MUST** be silently discarded.


### 5.2 Version
Identifies the protocol version.

This specification defines version `0x00`.

### 5.3 Request ID
A 32-bit unsigned integer generated by the client.

The server **MUST** copy the Request ID into the corresponding response.


### 5.4 Message Control
Identifies the message type and carries the return value.

## 6. Message Control
The Message Control field is a one-octet field containing the Message Type and Return Value.

| Bits | Field        | Description                                               |
| ---- | ------------ | --------------------------------------------------------- |
| 7-1  | Return Value | A 7-bit unsigned return value in the range `0x00`–`0x7F`. |
| 0    | Message Type | `0` indicates a `REQUEST`; `1` indicates a `RESPONSE`.    |

Bit 0 is the least significant bit of the octet.

In a `REQUEST`, the Return Value bits **MUST** be set to `0`.

In a RESPONSE, the Return Value bits indicate the result of processing the corresponding request. Return Values are defined in [Section 10](#10-return-values).

### 6.1 Field Encoding
The Message Control octet is encoded as follows:

`Message Control = (Return Value << 1) | Message Type`

The Message Type and Return Value can be decoded as follows:

`Message Type = Message Control & 0x01`

`Return Value = (Message Control >> 1) & 0x7F`

| Value  | Name       | Description |
| ------ | ---------- | ----------- |
| `0x00` | `DISCOVER` |
| `0x01` | `STATUS`   |
| `0x02` | `POWER`    |
| `0x03` | `UPDATE`   |
| `0x04` | `LOCK`     |


## 8. Protocol Operation
1. The client sends a `REQUEST`.
2. The server validates the packet.
3. If the packet is valid, the server processes the specified command.
4. The server sends a `RESPONSE` containing the same Request ID and Command as the corresponding request.
5. The Return Value in the response indicates whether the command completed successfully.
   
A server **MUST NOT** send more than one response for a single request.

Because UDP does not guarantee delivery, ordering, or duplicate suppression, a client **MAY** retransmit a request if no response is received. A server **SHOULD** use the Request ID to detect duplicate requests where executing a command more than once could produce unintended effects.


## 9. Error Handling
Packets **MUST** be discarded if:

- the magic value is invalid;
- the protocol version is unsupported;
- the packet is shorter than 10 octets;


## 10. Return Values
The Return Value indicates the result of processing a request.

In a `REQUEST`, the Return Value **MUST** be `0x00`.

In a `RESPONSE`, the following values are defined:
| Value         | Name              | Description                                                              |
| ------------- | ----------------- | ------------------------------------------------------------------------ |
| `0x00`        | `SUCCESS`         | The request was processed successfully.                                  |
| `0x01`        | `INVALID_REQUEST` | The request is structurally invalid or contains an invalid field value.  |
| `0x02`        | `UNKNOWN_COMMAND` | The Command is not recognized or supported by the server.                |
| `0x03`        | `INVALID_PAYLOAD` | The payload is missing, malformed, or invalid for the specified Command. |
| `0x04`        | `COMMAND_FAILED`  | The Command was recognized but could not be completed.                   |
| `0x05`        | `BUSY`            | The server is temporarily unable to process the request.                 |
| `0x06`        | `LOCKED`          | The server is currently locked by another client.                        |
| `0x07`        | `INTERNAL_ERROR`  | The server encountered an unexpected internal error.                     |
| `0x08`-`0x7f` | Reserved          | Reserved for future protocol versions or command-specific Return Values. |

A response with a Return Value other than `SUCCESS` **MUST** be treated as an unsuccessful operation.

Reserved Return Values **MUST NOT** be sent unless their meaning is defined by a later version of this specification or by the relevant Command definition.
